# Issue 不是个人主页的装饰

参与热门开源项目很诱人：提交一个 issue，贡献记录立刻出现在主页上。但如果问题没有复现、缺少环境信息，或者只是把使用疑问包装成 bug，它增加的是维护成本，而不是项目价值。

我给自己的原则是：**只有当报告能帮助维护者更快理解或定位问题时，才值得发送。**

## 提交前的五项检查

### 1. 使用最新稳定版本复现

旧版本中的问题可能已经修复。先记录：

- 项目版本或 commit；
- 操作系统与架构；
- 运行时版本；
- 安装方式；
- 最小配置。

“最新版”会随时间变化，不如写清楚具体版本。

### 2. 搜索重复问题

同时搜索：

- 报错原文；
- 关键函数或命令名；
- 相似行为描述；
- 已关闭 issue 与讨论区。

如果找到相似问题，优先补充新的复现证据，而不是再开一个标题不同的副本。

### 3. 构造最小复现

删除与问题无关的依赖、数据和业务代码，直到只剩触发问题所需的最小部分。最小复现可以是：

- 一段不超过几十行的代码；
- 一个只有必要文件的小仓库；
- 一组从空目录开始的终端命令；
- 一个公开且去除敏感信息的数据样例。

如果删除某段代码后问题消失，这段差异本身就是定位线索。

### 4. 区分“实际结果”和“预期结果”

不要只写“它坏了”。明确描述：

```text
实际：执行第二次请求时返回 500，并出现以下堆栈。
预期：同一配置下重复请求应返回与第一次相同的结果。
```

预期行为最好有文档、测试或既有 API 约定支撑。如果只是个人偏好，应标注为功能建议。

### 5. 清除敏感信息

日志中常见的敏感内容包括 API Key、访问令牌、邮箱、内网域名、用户目录和业务数据。发布前逐行检查，使用一致的占位符替换，并确认替换后仍可复现。

## 一个可直接使用的模板

```markdown
## Summary
一句话描述问题和影响。

## Environment
- Version / commit:
- OS and architecture:
- Runtime:
- Installation method:

## Minimal reproduction
从空环境开始的完整步骤或最小仓库链接。

## Expected behavior
应该发生什么，以及依据。

## Actual behavior
实际发生什么。

## Logs
经过脱敏、保持原始格式的日志。

## Additional context
已尝试的方法、回归范围或可能相关的代码位置。
```

## 什么时候不该发 issue

以下情况更适合先去讨论区、社区频道或本地排查：

- 尚未阅读安装文档；
- 无法在干净环境复现；
- 问题来自第三方插件但没有隔离；
- 只是询问“如何使用”；
- 只想让维护者替自己设计业务方案；
- 没有证据却断言某段代码是根因。

不开一个低质量 issue，也是一种对开源维护者的尊重。

## 从 issue 走向贡献

高质量报告之后，可以继续做小而明确的工作：

1. 在维护者确认方向后补一个失败测试；
2. 修正文档中导致误用的示例；
3. 提交只覆盖该问题的最小补丁；
4. 在 PR 中引用 issue，并说明验证方式。

贡献的含金量不取决于仓库有多少星，而取决于你的工作是否减少了不确定性。一个被顺利复现和修复的小问题，远比十个模糊报告更能建立可信度。
