# 我的 AI 辅助开发工作流

AI 编程最容易制造两种错觉：代码出现得很快，所以任务快完成了；回答写得很完整，所以结论已经可靠。真正进入项目后，最花时间的部分仍然是理解约束、处理边界、验证行为和留下维护线索。

我现在更愿意把 AI 当作一位速度很快、但必须接受明确验收的协作者。

## 第一步：把愿望改写成可验收的结果

“优化网站”不是任务，只是方向。一个可以执行的任务应该回答：

- 哪些页面或用户路径在范围内？
- 什么行为必须保持不变？
- 最终用什么证据判断完成？
- 哪些操作不可逆，必须先确认？

例如，我会把“把博客部署到自己的电脑”改写成：

> 静态站点监听本机回环地址；系统登录后自动启动；公网通过 Tunnel 访问；主页、分页、归档和搜索均返回 200；保留回退到旧源站的说明。

这段话同时给出了架构边界和验收条件，AI 才不容易把问题带向另一套方案。

## 第二步：先读项目，再提修改

我通常要求 AI 在动手前完成四件事：

1. 列出项目入口、构建命令和部署方式。
2. 找到与目标直接相关的文件。
3. 查看当前工作区是否有未提交修改。
4. 说明准备修改什么，以及为什么。

这一步看起来慢，实际上能减少大量返工。很多“模型写错代码”的根因，不是模型不会写，而是它在没有上下文时猜了一个看似合理的项目结构。

## 第三步：限制改动面

一次只解决一个闭环。修改内容模型时，不顺便更换 CSS 框架；修复路由时，不同时重构所有组件；提交开源 PR 时，不把格式化整个仓库混进功能补丁。

我会明确告诉 AI：

```text
只修改与这个问题直接相关的文件。
保留现有公共接口和视觉结构。
如发现相邻问题，先记录，不要顺手扩大范围。
```

小改动更容易审查、回滚，也更容易解释。

## 第四步：让验证成为交付的一部分

“已经修改”不是完成。不同任务至少要有一类验证：

| 任务 | 最低验证 |
| --- | --- |
| 内容修改 | 构建成功、链接可达、页面无明显溢出 |
| 路由修复 | 目标路径和相邻路径均测试 |
| 后台服务 | 进程状态、端口、日志和重启恢复 |
| API 修改 | 单元测试、类型检查或最小请求 |
| 开源 issue | 最新版本复现、重复搜索、最小样例 |

对于网站，我更喜欢同时验证“边缘返回 200”和“源站日志收到请求”。前者证明用户能访问，后者能排除缓存带来的假象。

## 第五步：把风险写进交付

可靠的交付不只展示成功，也说明运行条件。例如把 Mac 当服务器，就要写清楚它必须开机、联网、已登录且不能睡眠；使用免费 Tunnel，也要说明源站离线时网站仍会中断。

类似地，AI 生成的认证、权限、支付和数据迁移代码，即使通过基本测试，也应该由人进行额外审查。自动化能降低重复劳动，不能替代责任归属。

## 一个可复用的任务模板

```text
目标：
当前现象：
完成标准：
允许修改的范围：
必须保持不变：
可用的测试命令：
需要确认的外部操作：
```

这个模板没有“神奇关键词”，但它迫使我们先想清楚任务。通常，Prompt 质量的上限不是措辞，而是你对问题本身的理解。

## 最后

我判断 AI 工作流是否有效，不看它生成了多少行代码，而看三个结果：改动是否更容易审查，故障是否更容易定位，下一次维护是否不必从头猜测。

先约束，再生成，最后用证据验收。速度只是副产品。
